# ADR-0008: 모노레포 환경 ESLint, Tailwind, TypeScript 아키텍처 고도화 및 버전 업그레이드

## 📣 상태

채택됨 (Accepted) - 2026-04-16

## 📋 상황

2026년 4월, 프로젝트의 기반이 되는 핵심 도구들(ESLint 10, Tailwind CSS v4, TypeScript 6.0)의 메이저 업데이트가 진행됨에 따라, 기존 모노레포 설정 패키지(`@repo/eslint-config`, `@repo/tailwind-config`, `@repo/typescript-config`)에서 다음과 같은 치명적인 아키텍처 부채와 충돌 에러가 발생함.

### 주요 문제점 상세

#### 1. ESLint 10.2.0 호환성 붕괴 (`getFilename` 에러)

- **증상**: 기존에 사용하던 `eslint-plugin-react` 패키지가 ESLint 10의 Flat Config 구조와 호환되지 않음.
- **에러 로그**: `TypeError: contextOrFilename.getFilename is not a function` (React 버전 자동 추적 과정에서 발생)
- **위험성**: 설정 파일(`.mjs`)이나 특정 컴포넌트를 스캔할 때 린트 프로세스가 강제 종료되어 CI/CD 파이프라인이 마비됨.

#### 2. Tailwind CSS v4 패러다임 전환 및 JIT 캡슐화 붕괴

- **증상**: Tailwind v4 도입으로 CSS 자체를 설정 파일로 사용하는 구조로 변경됨.
- **위험성**: 기존 `@repo/ui`가 앱(`apps/blog`)에 소스 코드를 직접 참조(JIT)하게 만들고, `package.json`의 `exports`를 무분별하게 열어두어(Wildcard 매핑) **UI 패키지의 캡슐화가 완전히 붕괴**됨.

#### 3. TypeScript 6.0 도플갱어 (Doppelgänger) 에러

- **증상**: React 19의 새로운 타입(`VoidOrUndefinedOnly` 등)이 추가되면서, 워크스페이스 내 패키지들이 서로 다른 버전의 `@types/react`를 참조하여 타입 충돌 발생.
- **에러 로그**: `Two different types with this name exist, but they are unrelated.`

---

## ✋ 나의 생각

### 기존 구조를 유지할 수 있는가?

**✅ 결론: 불가능함. 즉각적인 아키텍처 리팩토링(Nuke and Pave) 필요.**

1. **레거시 플러그인의 한계**
   - `eslint-plugin-react`는 더 이상 모던 React 19 및 Next.js 16(App Router) 환경의 성능 최적화(Core Web Vitals)와 RSC 구조를 제대로 검증하지 못함.
2. **벤더(Vendor) 코드와의 린트 충돌**
   - 우리가 통제할 수 없는 외부 라이브러리(`shadcn/ui`, `react-bits`)에 사내의 깐깐한 린트 규칙을 강제하면 불필요한 유지보수 비용이 발생함. 방어적 린팅(Defensive Linting) 전략이 필요함.

3. **단일 진입점(Barrel File)의 부재**
   - UI 컴포넌트가 많아질수록 앱 쪽에서 내부 경로(`@repo/ui/src/shadcn/button`)를 직접 찌르는 행위는 나중에 UI 패키지 구조 변경 시 막대한 마이그레이션 비용을 초래함.

## 🔨 결정

**모노레포의 공용 설정 패키지를 전면 개편하고, `@repo/ui` 패키지를 '사전 빌드(Pre-build)' 기반의 캡슐화된 아키텍처로 초기화 및 재구축함.**

### 1. ESLint 아키텍처 고도화 (v10.2.0 대응)

- **플러그인 교체**: 레거시 `eslint-plugin-react`, `eslint-plugin-react-hooks`를 영구 퇴출하고, ESLint 10 네이티브를 지원하는 **`@eslint-react/eslint-plugin`**으로 전면 교체.
- **Overrides 패턴 적용 (방어적 린팅)**:
  - 공용 룰(`@repo/eslint-config`)은 엄격하게 유지.
  - `@repo/ui` 내부의 `src/shadcn`, `src/react-bits` 폴더는 예외 구역으로 지정하여 린트 검사를 무시(`off`) 처리. (내부 커스텀 코드와 외부 벤더 코드의 차별 대우)

### 2. Tailwind CSS v4 & 빌드 파이프라인 (tsup 연동)

- **공용 토큰 상속**: `@repo/ui/src/tailwind.css` 최상단에 `@import "@repo/tailwind-config/shared-styles.css"`를 선언하여 모노레포 디자인 토큰(Single Source of Truth) 강제.
- **JS/CSS 동시 빌드**: `tsup`과 `postcss`를 결합하여 컴포넌트와 스타일을 완전히 구워진(`dist/`) 형태로 납품. (`dev` 스크립트 시 둘 다 `--watch` 적용)

### 3. TypeScript 6.0 및 의존성 제어

- **타입 강제 통일 (PNPM Overrides)**: 루트 `package.json`에 `pnpm.overrides`를 선언하여 모노레포 전체가 동일한 `@types/react` 버전을 바라보도록 강제 (도플갱어 에러 원천 차단).
- **캡슐화 적용**: `@repo/ui`의 `exports`를 단일 진입점(`./tailwind`, `./tailwind.css`)으로만 제한하여 내부 폴더 구조 은닉.

## 📊 영향

### 📈 긍정적 영향

- **DX (개발자 경험) 극대화**: 린트 과정에서 발생하던 원인 모를 `getFilename` 에러와 TS 도플갱어 에러가 100% 소멸.
- **유지보수성 향상**: 외부 UI 라이브러리(`shadcn`) 업데이트 시 린트 에러 수정을 위해 코드를 뜯어고칠 필요가 없어짐.
- **아키텍처 안정성**: 앱(`apps/blog`)은 UI 패키지의 내부 구조를 몰라도 되므로, 향후 UI 패키지의 대대적인 리팩토링 시에도 앱 코드는 안전함.

### 📉 부정적 영향

- **없음**: 기존 얽혀있던 의존성을 덜어내어 빌드 속도가 오히려 향상되었으며, 트리 쉐이킹(Tree-shaking)을 통해 앱 번들 사이즈 증가는 발생하지 않음.

## 📝 고려한 대안

### 1. `eslint-plugin-react` 버전 강제 고정 및 수동 예외 처리

- **장점**: 당장 기존 설정을 크게 바꾸지 않아도 됨.
- **단점**: Flat Config 아키텍처와 본질적으로 맞지 않아 언제든 버그가 재발할 수 있으며, Next.js App Router 생태계와 룰 셋이 맞지 않음.
- **❌ 채택 안 함**: 낡은 기술 부채를 안고 갈 이유가 없음.

### 2. `@repo/ui` 컴포넌트 전체 경로 Export 허용

- **장점**: 개발할 때 자동 완성이 바로 잡혀 편할 수 있음.
- **단점**: 내부 구조 캡슐화가 붕괴되어 진정한 모노레포로서의 독립성이 사라짐.
- **❌ 채택 안 함**: 단일 진입점(Barrel File) 패턴이 장기적인 유지보수에 압도적으로 유리함.
